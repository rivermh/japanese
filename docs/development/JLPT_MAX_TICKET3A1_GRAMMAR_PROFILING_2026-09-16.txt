5. PROFILING UTILITY — WHAT WAS BUILT
================================================================================

Reviewed the existing `JlptMaxStagingProfilingReport.java` (412 lines, all
categories/note-types in one file, section D already does aggregate-only
Grammar profiling). Given how much additional note-level, DOM-structural, and
cross-tab detail Ticket 3A.1 asks for, extending that already-dense file
further would have hurt readability, so a **new, separate, Grammar-only**
test-scope file was created instead, following the same conventions already
established by `VocabularyNormalizationRealApkgReport.java` (Ticket 2's
analogous per-ticket real-apkg report):

- `GrammarNormalizationProfilingReport` (main tool, opt-in gated):
  - `-Djapanese.actual-apkg=<path>` opt-in only, `assumeTrue` skip otherwise
    (same gate as `PrivateApkgExtractorTest.optionalActualApkgRunsOnlyInFreshH2Staging`
    and the Ticket 1/2 report tools) — the general suite/CI never depends on
    the real apkg file.
  - Uses `PrivateApkgExtractor` into a fresh isolated in-memory H2 only
    (`jdbc:h2:mem:ticket3a1_grammar_profiling_<uuid>`), never a persistent or
    production DB.
  - Reads only `private_apkg_notes` columns already produced by the existing
    extractor (`category`, `tags`, `field_names`, `field_values`) — no ZIP
    media entry, no audio binary, no `SELECT *` into unrelated tables.
  - Writes a plain-text report to
    `build/reports/jlpt-max-profiling/grammar-profiling.txt` (build-output
    only, not committed).
  - Package-private `loadRows(Connection, ObjectMapper)` and
    `writeReport(List<Row>, PrintWriter)` are static and testable
    independently of the opt-in gate (this is what the synthetic test below
    exercises).
- `GrammarNormalizationProfilingReportSyntheticTest` (always-on sanity test,
  NOT opt-in gated): builds a tiny synthetic 4-note SQLite/APKG fixture (2
  normal-deck GRAMMAR notes + 2 종합 실전-deck COMPREHENSIVE notes, covering
  `<mark>` vs `div[lang=ja]` vs BackHTML-fallback cases, `IsSentenceArrangement`
  set on one note, varying `Kind` values), runs it through the real
  `PrivateApkgExtractor` + H2 + Flyway path exactly like production code would,
  then asserts `loadRows`/`writeReport` execute correctly and produce every
  expected report section. This proves the tool's logic works end-to-end
  without needing (or pretending to have) the real corpus.

Report sections implemented (mapped to ticket asks):
- §0: observed field-name schema for the Grammar model (self-verifies the
  assumed field names IsBasic/IsGrammarForm/IsPassageBlank/
  IsSentenceArrangement/Kind/UnitID/Level/FrontHTML/BackHTML rather than
  hardcoding them as fact).
- §5: Is* flag distinct raw values + full note-level
  (category, IsBasic, IsGrammarForm, IsPassageBlank, IsSentenceArrangement)
  combination counts.
- §6: Kind distinct raw values, x category, x Level, x Is*-combo.
- §7/8: normal-GRAMMAR FrontHTML structure — raw length stats, `<mark>` vs
  `div[lang=ja]` vs fallback presence/selection counts, selected-element text
  length stats + threshold buckets (>50/>80/>100/>120/>200), own-text-only and
  first-child-element length (candidate narrower boundaries), direct child
  tag/class frequency, and up to 8 structure-only skeletons (tag/class tree,
  <=12-char leaf fragments, never full copyrighted text).
- §9/10: COMPREHENSIVE BackHTML structure — descendant tag presence, div/
  section class frequency, other tag.class candidates, form/input/ol/ul/li/
  table/ruby presence, current selector hit-rates (`div._j4z`, `section._j4a`),
  heuristic choice/answer/blank/ordering text signals, and up to 8 skeletons.
- §11: IsSentenceArrangement-focused subset — category split, co-occurring
  flags, BackHTML signal comparison vs the rest of COMPREHENSIVE.
- §12: IsBasic/IsGrammarForm/IsPassageBlank sentinel-vs-subtype evidence
  (active/inactive category split + average FrontHTML/BackHTML length).
- §13: explanation>2000 broken down by category x (structured div._j4z vs
  back.text() fallback).
- §14: example-count distribution (min/max/avg/zero) for GRAMMAR vs
  COMPREHENSIVE via the current `section._j4a` selector.
- §15: UnitID non-blank/distinct counts + raw sample values by category (no
  invented prefix-parsing rule, per the ticket's explicit caution).
- §16: category x Level, and IsSentenceArrangement(set/empty) x Level.

Explicitly NOT built (out of Ticket 3A.1 scope, per section 19 of the brief):
GrammarNormalizationParser, any production Grammar/GrammarHtmlParser change,
any migration, candidate table, or ContentItem creation.
